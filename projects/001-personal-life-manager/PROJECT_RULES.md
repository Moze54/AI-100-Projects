# 项目规范

## 1. 当前阶段边界
当前阶段只进行产品定义、需求整理、竞品与市场研究、交互规划、安全和技术方案评估。

未经明确确认，不得：
- 创建业务代码或初始化应用工程。
- 安装依赖、生成构建配置或部署服务。
- 擅自确定客户端、服务端技术栈和云服务商。
- 将未确认的讨论结论写成已定需求。
- 为追求功能数量而扩大首发范围。

## 2. 事实状态标记
- 已确定：用户明确确认的方向或规则。
- 建议：当前推荐方案，仍需确认。
- 待评估：需要调研、测试或成本测算。
- 暂不做：明确排除当前范围。
- 已废弃：曾讨论但已被替代的方案。

不能将建议、假设或未经验证的市场信息描述为事实。

## 3. 产品设计原则
- 以真实用户问题为起点，不以技术能力堆功能。
- 优先解决资料保存、事项管理、日期提醒的核心闭环。
- 快速录入优先，避免强制填写和复杂表单。
- 本地优先、隐私优先、用户可控。
- 模块边界清晰，资料、事项、附件和保险箱职责明确。
- 首发范围必须可独立交付，不依赖尚未完成的云服务。
- 所有重要数据操作都应考虑导出、迁移和删除。

## 4. 文档规范
- 使用 Markdown。
- 产品文档统一使用中文，必要英文术语首次出现时附中文解释。
- 每份文档标明版本、状态和更新时间。
- 功能清单按模块拆分，颗粒度应足以独立讨论和验收。
- 需求变化时同步更新 PRD、功能清单、产品规则和路线图。
- FEATURE_LIST.md 是功能条目的主清单，避免重复维护矛盾清单。
- 重大决策记录原因、影响范围和待解决问题。

## 5. 安全与隐私
- 不提交真实用户资料、证件图片、账号密码、密钥、令牌或生产数据。
- 示例数据必须虚构。
- 不把密钥、密码、敏感字段写入日志或错误信息。
- 加密、密钥恢复、设备授权、云同步和删除语义必须经过专项设计。
- 不以“服务端只存密文”推导出平台没有个人信息合规责任。
- 健康、证件和保险箱数据采用与敏感级别相匹配的保护措施。

## 6. 需求验收
每个进入开发的功能至少明确：
- 用户目标与使用场景。
- 前置条件和权限要求。
- 正常流程。
- 空状态、错误状态和边界情况。
- 数据创建、修改、删除和恢复行为。
- 隐私与同步行为。
- 可验证的验收标准。

## 7. 版本与范围控制
- P0 为核心首发范围，P1 为重要增强，P2 为后续能力。
- 进入开发前必须完成范围冻结和依赖梳理。
- 新增需求说明价值、成本、风险和对现有范围的影响。
- 不以“以后可能用到”为理由提前建设复杂基础设施。
